Hexagonal mental model

The application core lives in the Node host process. React is presentation — outside the hexagon — and calls in through a Host API client. External systems (Essentials project on disk, LLM APIs) sit on the driven side.

Hexagonal term What it represents In this app
Presentation UI + client that forwards user intent renderer/components, App.tsx, host-api/*
Driving port Use cases the app exposes to actors handleReadMap, handleAIChat, … (handlers.ts)
Driving adapters Translate wire protocol → use case calls electron-ipc.ts · http-api.ts (split)

Driven port What the core needs from outside Read/write opened game project · call LLM
Driven adapters Implement those needs project-data-client · ai-service-*
External systems Authoritative stores the app must not re-invent Essentials project Data/ · Anthropic / Google APIs
Host API client is not a hexagon adapter. It is the presentation-layer proxy that reaches the driving port — the caller side of the same API the driving adapters implement on the server side.
Project data layer = filesystem I/O for the opened game project. Format-specific code (Marshal, Ruby, .rxdata) lives only under project-data/implementations/.

Why this stack?

Electron + React

Desktop app needs filesystem access, native dialogs, and long sessions. Electron wraps Chromium + Node; React workbench in the renderer process.

Project data layer

Generic filesystem I/O for the opened game project. Current format handler: implementations/marshal-ruby/ — not part of the layer name.

On Essentials, not custom format

Playable games in the existing fan-dev ecosystem. Custom JSON/SQLite would require a full runtime rewrite.

Split driving adapters

IPC for Electron shell (push events, native dialogs). HTTP for browser host and Playwright. Both call the same handlers.ts — not two backends.

ADR 0001

Local-first, Essentials-compatible, Ruby-only disk writes (no TS Marshal fallback). See docs/adr/0001-local-first-ruby-bridge.md.

Poor fits at this scale

Unity/Godot rewrite, microservices from day one, cloud-only SaaS without local disk access.

Naming rules

  • Project data layer — project-data-client + project-data/implementations/*
  • Host API — presentation proxy to driving port; split ipc + http transports
  • Driving adapters — split ipc + http on main side
  • No generic “bridge” — see CONTEXT.md

Why shared/?

Electron forbids importing main-process code in the renderer. Shared holds types and pure functions both sides need: map tree logic, delete rules, read→preview transforms. No fs, no window, no AI keys.

Local vs remote backend

Stay local (now)

  • User’s Essentials folder stays on their machine
  • Project data layer requires local filesystem access
  • No hosting cost, no map asset upload privacy issues
  • MVP: AI keys can stay local (user-provided)

Add remote services (later)

  • Hosted AI proxy (hide keys, rate limits, billing)
  • Team collaboration / shared Game Bible
  • Heavy vision jobs (tileset labeling at scale)

Design impact: Keep handlers.ts as application core. Remote becomes another driven adapter — same pattern as project-data and LLM clients. Host API http-transport gets a configurable base URL; domain logic does not move to a cloud monolith.

CQRS (and how this project uses it)

CQRS = Command Query Responsibility Segregation. Separate the read model (queries, previews, summaries) from the write model (commands, patches, file writes).

Here: read-map / preview canvas = query side. Chat → MapPatch → executor → project-data write = command side. Planned specialists produce patches (commands); validator + executor apply them. Clear read vs write paths and patch-first edits — no event sourcing required.

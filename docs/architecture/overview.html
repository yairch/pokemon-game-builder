Architecture reference

Pokemon Game Builder

AI-first companion for RPG Maker XP + Pokémon Essentials. Local app writes real .rxdata files; React UI previews and iterates without opening RMXP daily.

Why this stack?

Electron + React

Desktop app needs filesystem access, native dialogs, and long sessions. Electron wraps Chromium + Node; React is your TS UI skill from RN. Together: one codebase, local-first, no server to deploy for MVP.

Ruby bridge

RMXP stores maps as Ruby Marshal blobs. Ruby reads/writes them natively. Reimplementing Marshal in TS is high risk for a POC; Ruby is a thin adapter at the disk seam.

On Essentials, not custom format

Product goal: playable games in the existing fan-dev ecosystem. Custom JSON/SQLite would require a full runtime rewrite. Essentials compatibility is the moat and the constraint.

.rxdata files

Industry-standard for this niche (RMXP). Round-trip fidelity with Game.exe smoke tests. Trade-off: opaque binary, Ruby dependency, no git-friendly diffs.

Replace Ruby later?

Only if you leave RMXP entirely. While targeting Essentials, Ruby (or a proven Marshal library) stays. A TS-only path means owning serialization + every RPG::Map edge case.

Poor fits at this scale

Unity/Godot rewrite, microservices from day one, cloud-only SaaS without local disk access, or Tauri+Rust if team lacks systems skills and Ruby bridge already works.

Layer architecture

Hexagonal / ports-and-adapters: domain logic in the center; UI and I/O are adapters.

“Local backend” = Node in Electron main process (or standalone via browser-server.ts). Not a remote server — it runs on the user’s machine with filesystem access.

Components — learning order

  1. 1

    shared/types.ts + pure modules

    Domain types (MapData, MapSpec) and logic with no Electron/React imports: tree building, delete integrity, map transforms. Testable everywhere.

  2. 2

    MapGenerator + marshal_handler.rb

    Spawns Ruby with JSON args; reads/writes binary RMXP structures. The disk I/O adapter.

  3. 3

    handlers.ts

    All use cases: chat, read map, delete preflight, tileset inspector. Single entry for IPC and HTTP. Not Electron-specific.

  4. 4

    ipc-handlers.ts / api-server.ts

    Thin adapters mapping channels/routes → handler functions. Browser dev uses Express on :3001; Electron uses ipcMain.

  5. 5

    bridge.ts (renderer)

    Unified client: window.electron.invoke in desktop, fetch to Express in browser mode. UI never imports Electron directly.

  6. 6

    App.tsx — your app shell, not framework infra

    Root React component: holds project path, chat messages, preview state, map tree. Same role as your RN root navigator + screen state — project-specific, not provided by Electron/React.

  7. 7

    Workbench components

    MapPreview (canvas), MapsTree (dnd-kit), ChatInterface, modals. Presentation only; call bridge for data.

File structure critique

Works well

  • main/ vs renderer/ vs shared/ — standard Electron split
  • shared/ — pure TS usable from main and renderer tests
  • Handlers separated from transport — interview-ready hexagonal story
  • docs/plans/ + VISION.md — product north star

Improve over time

  • handlers.ts is large (~1000+ lines) — split by domain when executor lands
  • No docs/adr/ yet — record stack + patch-first decisions
  • docs/prompts/ planned but missing — agent layer not in repo
  • README was stale vs actual stack — now fixed separately

Why shared/?

Electron forbids importing main-process code in renderer. Shared holds types and pure functions both sides need: map tree logic, delete rules, read→preview transforms. No fs, no window, no AI keys.

Local vs remote backend

Stay local (now)

  • User’s Essentials folder stays on their machine
  • No hosting cost, no map asset upload privacy issues
  • Ruby spawn + large file I/O fit local process
  • MVP: AI keys can stay local (user-provided)

Add remote services (later)

  • Hosted AI proxy (hide keys, rate limits, billing)
  • Team collaboration / shared Game Bible
  • Heavy vision jobs (tileset labeling at scale)
  • Analytics, template marketplace

Design impact: Keep handlers.ts as domain core. Remote becomes another adapter (HTTP client to your Scala/Protobuf service) — same pattern as IPC today. Renderer unchanged if bridge targets configurable base URL. Do not merge domain logic into a cloud monolith early.

CQRS (and how this project uses it)

CQRS = Command Query Responsibility Segregation. Separate the read model (queries, previews, summaries) from the write model (commands, patches, file writes).

Here: read-map / preview canvas = query side. Chat → MapPatch → executor → Ruby write = command side. Planned specialists produce patches (commands); validator + executor apply them. You don’t need event sourcing or separate databases to benefit from the split — just clear read vs write paths and patch-first edits.
